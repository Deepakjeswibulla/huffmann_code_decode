Huffmann Code Decode

A C++20 implementation of Huffman coding for lossless file compression and decompression, built from scratch using standard C++ libraries.

The project takes an input file, analyzes the frequency of each byte, constructs a Huffman tree, generates variable-length binary codes, packs those bits into bytes, and writes a self-contained compressed file. The decoder reads the stored metadata, reconstructs the Huffman tree, and restores the original file.

How Huffman Coding Works

Huffman coding is a greedy lossless compression algorithm.

It assigns shorter binary codes to frequently occurring symbols and longer codes to less frequent symbols.

For example, consider:

ABCDAA

The frequencies are:

A → 3
B → 1
C → 1
D → 1

The Huffman algorithm uses these frequencies to construct a binary tree.

One possible tree is:

             *
            / \
           A   *
              / \
             D   *
                / \
               B   C

Traversing the tree using:

left  → 0
right → 1

produces:

A → 0
D → 10
B → 110
C → 111

Therefore:

ABCDAA

becomes:

0 110 111 10 0 0

or:

01101111000

These are bits, not characters. The implementation packs the bits into bytes before writing them to disk.

Why Does the Original Order Not Matter When Building the Tree?

The Huffman tree is constructed from frequency, not from the position of characters in the input.

For:

ABCDAA

the tree only needs:

A → 3
B → 1
C → 1
D → 1

However, when encoding the file, the original sequence is processed from beginning to end:

A B C D A A
↓ ↓ ↓ ↓ ↓ ↓
0 110 111 10 0 0

Therefore, the encoded bit stream preserves the original ordering.

During decompression, those bits are read sequentially and converted back into:

A B C D A A
Equal Frequencies

When multiple symbols have the same frequency, multiple valid Huffman trees can exist.

For example:

B → 1
C → 1
D → 1

does not force a unique ordering between B, C, and D.

Different valid trees may therefore generate different codes.

This is not a problem.

The important requirement is that the encoder and decoder reconstruct the same tree from the stored metadata.

Compression Process

The compression pipeline is:

                    Input File
                        │
                        ▼
                  Read Raw Bytes
                        │
                        ▼
                Frequency Analysis
                        │
                        ▼
                    Min-Heap
                        │
                        ▼
                 Huffman Tree
                        │
                        ▼
                Generate Codes
                        │
                        ▼
                  Encode Bytes
                        │
                        ▼
                 Pack Bits
                        │
                        ▼
          Write Metadata + Bit Stream
                        │
                        ▼
                  .huff File
Step 1 — Read the input

The file is opened in binary mode and read byte-by-byte.

Step 2 — Count frequencies

Every unique byte is counted.

Step 3 — Build the tree

A priority queue is used to repeatedly select the two least-frequent nodes.

Step 4 — Generate codes

The tree is traversed recursively.

left  → 0
right → 1
Step 5 — Encode

Each original byte is replaced by its Huffman code.

Step 6 — Pack bits

Individual bits are packed into actual bytes.

Step 7 — Write the archive

Metadata and compressed data are written to the .huff file.

Decompression Process

The decompression pipeline is:

                  .huff File
                      │
                      ▼
                 Read Metadata
                      │
                      ▼
              Read Frequencies
                      │
                      ▼
              Rebuild Huffman Tree
                      │
                      ▼
              Read Encoded Bits
                      │
                      ▼
             Traverse Huffman Tree
                      │
                      ▼
               Recover Bytes
                      │
                      ▼
                Output File

The decoder does not need the original input file.

It reconstructs the Huffman tree using the information stored inside the compressed file.

Compressed File Format

The .huff file contains the metadata required for decompression along with the compressed bit stream.

Conceptually:

┌──────────────────────────────┐
│ Number of unique bytes       │
├──────────────────────────────┤
│ Byte + frequency entries     │
├──────────────────────────────┤
│ Original file size           │
├──────────────────────────────┤
│ Compressed bit stream        │
└──────────────────────────────┘
Frequency Table

The frequency table allows the decoder to reconstruct the Huffman tree.

This is important because the tree used during compression does not remain in memory after the program terminates.

The compressed file contains enough information to rebuild it.

Original File Size

Huffman codes do not necessarily produce a number of bits divisible by 8.

For example:

101101

contains only six bits.

Since files are written in complete bytes, the final byte needs padding:

10110100

The extra bits are not part of the original compressed data.

The original file size allows the decoder to stop after reconstructing the correct number of original bytes.

Bit-Level Encoding

A major part of the implementation is handling individual bits.

Consider:

A → 0
B → 110
C → 111

For:

ABC

the encoded stream is:

0 110 111

which becomes:

0110111

This is seven bits.

The implementation does not store:

'0'
'1'
'1'
'0'
'1'
'1'
'1'

as separate characters.

Instead, it packs them into a byte.

This is essential for achieving actual bit-level compression.

Binary File Support

The implementation processes raw bytes rather than assuming the input is text.

This allows testing with files such as:

.txt
.cpp
.py
.csv
.json
.bin
.dat

and other arbitrary byte sequences.

It can also process bytes containing values outside the printable ASCII range.

Compression Limitations

Huffman coding does not guarantee that every input file will become smaller.

For very small files, the metadata stored in the .huff file can be larger than the compression savings.

Files that are already compressed may also provide little or no benefit.

Examples include:

.jpg
.png
.zip
.mp4

This is expected behavior.

The primary requirement of this project is lossless reconstruction, not guaranteed size reduction for every possible input.

Design Decisions
Why Huffman Coding?

Huffman coding is a classic greedy algorithm that demonstrates how statistical properties of data can be exploited for lossless compression.

Why a Priority Queue?

At every tree-building step, the two least-frequent nodes must be selected efficiently.

A min-heap provides an appropriate data structure for this operation.

Why Process Bytes?

Processing raw bytes makes the implementation applicable to both text and binary files.

Why Store Frequencies?

The decoder needs to reconstruct the Huffman tree.

Storing the frequency information makes the compressed file independently decodable.

Why Pack Bits?

Huffman codes operate at the bit level.

Packing the bits into bytes avoids wasting space by storing binary digits as normal characters.
